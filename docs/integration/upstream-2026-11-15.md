# Upstream integration: behavior and rollout boundaries

Compared fork `8865b2752` with upstream `123fe899c`. This integration is a
source synchronization, **not approval to deploy or migrate production data**.
The fork bootstrap imported an older runtime snapshot. Many apparent fork
changes reverse ancestor fixes rather than represent features to reimplement.
Use the coordinated upstream runtime and retain intentional packaging and
operational differences, not two parallel tenancy implementations.

## Feature mapping

| Fork behavior | Upstream equivalent / integration decision |
| --- | --- |
| Inline tenancy predicates and request scoping | `lib/tenancy/policy.py`, `resources.py`, middleware and core hook registry. Preserve upstream ACL hardening, including shared-mode isolation and destructive-action permissions. |
| Inline task tenant/visibility columns | `task_acl` side table. This is a data migration boundary, not just a source rename. |
| `web.users.Tenant` / tenant fields on UserProfile | `cape_tenancy.Tenant`, `UserTenantMembership`, `GroupSandboxPolicy`. Existing Django rows are not automatically equivalent to fresh plugin rows. |
| Central S3/local artifacts | `lib/tenancy/storage`, supporting S3/GCS/Azure/local, with legacy `[central_mode]` and configuration-key aliases. **Object-key identity changed.** |
| Broker HTTP / DynamoDB worker lookup | Both retained in `lib/tenancy/storage/job_directory.py`. HTTP still calls `/api/status/{job_id}`. The default changed from DynamoDB to `broker_http`; configure the intended backend explicitly. |
| Guacamole operator authorization | Upstream `_is_direct_vnc_authorized` and task-manage checks replace old inline tenancy calls. |
| Direct-console busy-VM protection | Upstream lock-dependent checks were not equivalent. Preserve the fork's independent task/unfinished-guest, fail-closed preflight check before console access and VM start, using upstream transaction helpers. A scheduler race after preflight is not eliminated by this check. |
| `Tenant.retention_days` | Fork has a field and migration only; no tracked runtime consumer was found. Upstream plugin Tenant lacks it. Preserve values in the pre-migration export; do not claim automatic retention or silently discard the metadata. A plugin-field/data migration needs an explicit retention design. |
| Debian/AMI pipeline, EICAR gate, normalization package | Fork-only deployment layer, retained separately from upstream runtime. |

## Mandatory staging migration review before rollout

1. Back up and rehearse recovery for SQL, Django, MongoDB and object storage.
   Capture current heads, enabled tenancy/storage settings, explicit job-directory
   backend and worker/UI topology. Do not run a production bake or auto-promote.
2. Export existing task tenant IDs, visibility, ownership and report bindings,
   plus legacy Django tenants, memberships, admin groups and retention values.
   Upstream Alembic `6_drop_inline_tenancy_columns.py` drops `tasks.tenant_id`
   and `tasks.visibility` without copying them and has no downgrade.
   Upstream Django tenancy `0001_initial` creates new plugin tables; it is not a
   legacy `users_tenant` import. Design and validate the mapping **before** these
   columns disappear. Preserve tenant identity or remap every ACL reference.
3. Validate task attributes and worker-to-main mapping. Upstream uses universal
   `Task.attributes`, including `main_task_id`, `task_acl`, correlation fields
   and arbitrary attributes. External broker identifiers must not be treated as
   authorization or numeric central task identity.
4. Inventory historical artifact prefixes (`results/<job_id>`, including
   `ui-<id>` / `local-<id>` and external broker IDs). New storage readers address
   `results/<numeric-task-id>`. Configuration aliases do not rewrite old keys.
   Plan collision-safe object migration or a reviewed compatibility reader,
   verify report-to-task binding, and retain old objects until access tests pass.
5. Reconcile ACL/report stamps and bridge state in staging, then verify isolation
   for public, tenant and private reports across multiple tenants, including
   foreign/stale report stamps and unmapped worker uploads. Confirm artifacts,
   comments, deletes, reprocessing, resubmission and live-console routing.
6. Test Guacamole identity across numeric and legacy `ui-N` broker keys. Exercise
   direct-console access while a task is running but its VM lock is not yet set,
   unfinished guests, and SQL failures. All must refuse direct-console access.
7. Run package build and isolated EICAR end-to-end gates against the staged stack.
   Record old/new record counts, unresolved mappings and rollback results. Only
   after these pass should a separate production migration be proposed.

The migration review should be cross-checked against the owner's detailed
[upstream #3377 review](https://github.com/kevoreilly/CAPEv2/pull/3377#issuecomment-6670354111)
and subsequent [#3387 fixes](https://github.com/kevoreilly/CAPEv2/pull/3387).
Source inclusion of those fixes does not prove historical deployment data has
been migrated successfully.

## Focused verification

`python -m unittest discover -s tests/web -p test_direct_vnc_analysis_guard.py -q`
checks the preserved direct-console safety behavior without booting Django or
libvirt. These tests execute extracted production functions with substituted
DB boundaries; they do not replace database, web or live-VM integration tests.

## Reconcile dry-run safety

`utils/tenancy_reconcile.py --dry-run` now bypasses the normal database initializer,
which otherwise creates tables and inserts the Alembic version even before report
reconciliation. Dry-run requires existing `tasks`, `task_acl` and migrated task
attributes; missing schema is an error, not an invitation to initialize it.
SQLite is opened read-only without creating a missing file; PostgreSQL sessions
are read-only. No migration or ACL bootstrap is performed by this mode. Run the
separately reviewed migration plan first if the dry-run reports missing schema.
